# Decisions

## ADR Acceptance and Decision Summaries

ADR-005 standardizes `Accepted` as the status for every committed ADR and treats merge of a pull request containing an ADR as the normal act of acceptance.  Supersession, replacement, deprecation, and similar relationships are recorded in ADR narrative sections rather than alternate status values, so historical decisions remain accepted records even when newer decisions govern.  Repositories that use ADRs must maintain `doc/decisions.md`, with one generally three-to-five-sentence summary per ADR and a direct reference to the governing record.  Adding or materially changing an ADR requires reviewing and updating the corresponding decision summary in the same pull request.  See [ADR-005: Standardize ADR Acceptance and Decision Summaries](adr/ADR-005-standardize-adr-acceptance-and-decision-summaries.md).

## JavaScript Documentation Standard

ADR-004 adds a reusable JavaScript documentation standard based on JSDoc and establishes JSDoc comments as the maintained source of truth for projects that adopt it.  The canonical required-parameter form is `@param {Type} name - Description.`, while the source standard also covers broader JSDoc constructs independently of the current `javascript-doxygen` implementation boundary.  `javascript-doxygen` is the designated Doxygen input-filter project when translation is required, but that repository separately governs and tests the subset it actually translates.  TypeScript and TSDoc remain outside this decision.  See [ADR-004: Add a JavaScript Documentation Standard Based on JSDoc](adr/ADR-004-add-javascript-documentation-standard.md).

## Release Artifacts and Standards Adoption

ADR-003 defines the current release and consumer-adoption contract: one complete standards archive, one SHA-256 checksum, a committed `doc/standards/` snapshot, and provenance recorded in `.codingstandardrc`.  A maintainer or coding agent performs adoption externally, verifies a concrete release, replaces the managed standards tree, updates repository-facing governance, and proposes the result through a pull request.  Consumers do not need permanent standards-fetching machinery such as updater workflows, Bashdeps manifests, or Make synchronization targets.  This decision supersedes ADR-002's consumer-installed updater while retaining the complete archive and committed-snapshot model.  See [ADR-003: Release Artifacts and Agent-Mediated Standards Adoption](adr/ADR-003-release-artifacts-and-agent-mediated-adoption.md).

## Single Archive and Consumer Update Workflow

ADR-002 replaced ADR-001's language-oriented profile archives with one complete deterministic standards archive because applicability is a governance concern rather than a packaging concern.  It retained committed consumer snapshots and introduced a manually dispatched consumer-side workflow that verified a selected release, replaced `doc/standards/`, and proposed the resulting update.  Experience later showed that installing update machinery in every consumer created more maintenance than value, so ADR-003 superseded the workflow portion of this design with agent- or maintainer-mediated adoption.  ADR-002 remains an accepted historical decision that explains the transition from profile packaging to the current single-archive model.  See [ADR-002: Use One Standards Archive and a Consumer Update Workflow](adr/ADR-002-single-archive-consumer-workflow.md).

## Profile Archive Distribution

ADR-001 introduced deterministic profile archives so consumers could adopt reusable standards without declaring every individual source file.  It also established two ideas that remain important: committed standards snapshots for offline and agent use, and a separation between verified byte acquisition and archive interpretation.  Language-specific packaging ultimately proved more complex than useful, and ADR-002 superseded that portion of the design with one complete archive per release.  ADR-001 remains an accepted historical decision and provides the rationale for the repository's earliest reusable distribution model.  See [ADR-001: Distribute Standards as Profile Archives](adr/ADR-001-profile-archive-distribution.md).
